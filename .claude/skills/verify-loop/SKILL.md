# 検証ループの省トークン実行

AGENTS.md の検証ループを回すときの実行順とログの扱い。**出力は tail で刈る**のが原則
（フルテストは 400 件超・約 75〜95 秒。生ログを全部読むと数千トークン溶ける）。

## 実行順（速い順に失敗を早期検出）

```bash
npm run typecheck                                   # 数秒。型崩れを最初に潰す
npx vitest run <変更に直接関係する *.test.ts> 2>&1 | tail -20   # 対象だけ先に
npm test 2>&1 | tail -8                             # フル（balance 含む・約90秒）
npm run lint 2>&1 | tail -3
npm run build 2>&1 | tail -2
```

- 失敗したときだけ、そのテストを `-t "テスト名"` で単独再実行して詳細を見る。
- **フルテストは原則1回**（最後に）。途中の試行錯誤は対象ファイル単位で回す。
- 長い調査（失敗が多発・原因不明）になったら、修正→再実行のループごと
  general-purpose サブエージェントへ委任し、「直した内容＋green の証跡（末尾数行）」
  だけ返させる。

## このプロジェクト固有の合格ライン

- `src/game/balance.test.ts` はバランスの両原則を固定している：
  **「第5面以降は連打（全員おまかせ）で勝てない」**と**「第6面は対処プレイで無被弾・
  膜消費ほぼゼロで勝てる」**。どちらか一方でも崩れたら、テストを緩める前に
  ボット（＝正しいプレイの定義）を新メカニクスに適応させられないか先に検討する
  （前例：パリィの威力引き算化で「結界役1人が両極維持＋2人ひるみロック」へボットを更新）。
- 受け入れ条件は graph_mage-spec.md の該当機能と照合してから「完了」と言う。
- 1つでも赤のまま完了宣言しない（AGENTS.md）。

## 付随の小技

- GitHub Actions の結果確認（デプロイ等）：`mcp__github__actions_list` の応答は 300KB 超で
  保存ファイルに落ちる。**中身は python の json 読みで先頭2件だけ抜く**：
  `python3 -c "import json; d=json.load(open('<保存パス>')); [print(r['id'], r['head_sha'][:7], r['status'], r['conclusion']) for r in d['workflow_runs'][:2]]"`
- dev サーバの停止は `pkill -f vite` を**単独コマンド**で（&&チェーンに入れると exit 144）。
