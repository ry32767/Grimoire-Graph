# Issue 一括対応（Batch Issue Implementation）

過去のセッションで最も多い作業形態（「issue #1-17 大規模改修」「敵仕様修正（#46〜#51）」「戦闘バグ10件を修正」等）。複数の issue・フィードバック項目をまとめて実装する。

## 手順

### 1. 収集と整理

- issue 番号が指定されていれば GitHub MCP ツール（`mcp__github__issue_read` / `list_issues`）で本文を取得する。テストプレイのフィードバックが文章で渡された場合は項目に分解して番号を振る。
- 各項目を分類する：
  - **bug** — 仕様どおり動いていない（仕様が合格ライン）
  - **feat** — 仕様の追加・変更を伴う（`graph_mage-spec.md` の更新が必要）
  - **tweak** — 演出・バランスの調整（`docs/` の該当ページ更新が必要なことが多い）
- 項目間の依存関係（例：定数の整理 → それを使う新挙動）を見て実装順を決める。TaskCreate で項目ごとにタスク登録すると進捗が追いやすい。

### 2. 項目ごとに実装

各項目について：

1. 仕様の該当箇所（`graph_mage-spec.md`・`docs/`）を読み、合格ラインを明文化する。仕様に書かれていない新挙動なら、先に spec に受け入れ条件を追記する。
2. 実装する。ゲームロジックは `src/game/` の純粋関数、定数は `src/data/constants.ts` に置く（AGENTS.md のコーディング規約に従う）。
3. テストが書ける条件は先にテストを書く（テストが合格ライン）。
4. その項目の受け入れ条件を ○× で照合する。

### 3. 仕上げ

1. `verify-loop` スキルで全体を green にする。
2. 仕様・数値・挙動を変えた項目は `docs-sync` スキルの対応表でドキュメントを更新する。
3. コミットメッセージはこのリポジトリの流儀に合わせる：
   - 形式：`feat:`/`fix:`/`tweak:`/`docs:` ＋ 日本語の要約 ＋ 末尾に issue 番号（例：`fix: 暴発AoEが撃破済みの敵にダメージ判定を出す不具合を修正（#42）`）
   - 関連の強い数項目は1コミットにまとめてよいが、無関係な項目は分ける。
4. 報告は「項目ごとの対応結果（issue番号 → 何をどう直したか → 受け入れ条件○×）」の一覧にする。未対応・保留にした項目は理由を明記する。

## 注意

- 項目数が多くても**検証ループを最後に1回だけ**にしない。まとまり（2〜4項目）ごとに `npm test` と `npm run typecheck` を回し、壊した箇所を早く特定する。
- 仕様の解釈が割れる項目は実装前にユーザーへ確認するか、`graph_mage-spec.md` の「9. 未決定事項 / 要確認」に追記する。
